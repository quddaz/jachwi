# 인증·매물·체크 결과 확장 설계

## 목표

현재 OAuth/JWT 및 사용자 체크리스트 기반 코드에 Refresh Token 보안 흐름, 회원 조회, 매물과 메모, 매물 체크리스트 스냅샷과 결과·진행률 API를 추가한다.

사진 저장소 연동은 이번 범위에서 제외한다. 따라서 매물 삭제는 DB 종속 데이터만 트랜잭션으로 삭제하며 외부 사진 객체 정리는 사진 기능 구현 시 추가한다.

## 공통 원칙

- Spring Data JDBC/JPA를 사용하지 않고 저장소 인터페이스와 `JdbcTemplate` 구현체를 둔다.
- SQL은 각 JDBC 저장소 메소드 내부에 둔다.
- 계층은 Controller → Service → Repository 방향만 허용한다.
- 요청 DTO가 서비스 명령으로, 서비스 결과가 응답 DTO로 변환되는 책임을 가진다.
- Lombok은 `@Getter`, `@Slf4j`만 사용한다.
- 도메인 객체에는 필요한 최소 불변식만 검사하고 요청 정책과 복합 검증은 서비스 하위 `policy`, `validation` 클래스에 둔다.
- 다른 회원의 자원은 전용 `*_NOT_FOUND` 오류와 `404 Not Found`로 숨긴다.
- 생성·교체·전체 저장처럼 여러 SQL이 함께 성공해야 하는 흐름은 서비스 트랜잭션으로 묶는다.
- 서비스 테스트는 MySQL Testcontainers 기반 통합 테스트로 작성한다.

## 1. 인증과 회원

### Refresh Token

- Refresh Token은 256비트 이상의 암호학적 난수로 생성하는 불투명 토큰이다.
- 원문은 로그인 또는 회전 응답에서 한 번만 반환한다.
- 저장소에는 SHA-256 해시, 회원 ID, 만료 시각, 폐기 시각만 저장한다.
- 로그인 성공 트랜잭션에서 회원 저장과 Refresh Token 저장을 함께 처리한다.
- `POST /api/auth/tokens`는 토큰 해시로 행을 잠금 조회한다.
- 유효한 토큰이면 기존 행의 `revoked_at`을 기록한 뒤 새 Access Token과 Refresh Token을 발급한다.
- 만료 토큰은 `REFRESH_TOKEN_EXPIRED`, 존재하지 않는 토큰은 `REFRESH_TOKEN_INVALID`다.
- 이미 폐기된 토큰이 재사용되면 `REFRESH_TOKEN_REUSED`를 반환하고 해당 회원의 모든 활성 Refresh Token을 폐기해 재로그인을 요구한다.
- 동시 회전 요청 중 하나만 성공하며 나머지는 재사용 감지 흐름을 따른다.

### 로그아웃과 회원 조회

- `POST /api/auth/logout`은 Access Token으로 인증된 회원과 요청 Refresh Token의 소유자가 일치할 때 현재 토큰만 폐기한다.
- 유효하지 않거나 다른 회원의 Refresh Token은 인증 정보를 노출하지 않는 오류로 처리한다.
- `GET /api/members/me`는 요청 속성에 저장된 회원 ID로 회원을 조회해 ID, 이름, 이메일을 반환한다.

### 필터 오류

- 공개 경로는 OAuth 로그인, Refresh Token 회전, 시스템 체크 항목 조회다.
- 그 외 `/api/**` 경로에는 Bearer Access Token이 필수다.
- 토큰 누락, 잘못된 Bearer 형식, 서명·issuer·audience 오류, 만료는 필터에서 공통 JSON `401 Unauthorized`로 응답한다.
- 필터는 공통 오류 응답 DTO와 `ObjectMapper`를 재사용하며 토큰 원문을 응답이나 로그에 포함하지 않는다.

## 2. 매물

### 생성과 제한

- 매물은 회원 ID, 이름, 선택 금액 3종, 주소, 발견 경로와 최근 활동 시각을 가진다.
- 이름은 trim 후 1~50자, 금액은 `null` 또는 0 이상의 정수, 주소와 발견 경로는 `null` 또는 최대 500자다.
- 회원 행을 잠근 뒤 소유 매물 수를 조회하고 50개 미만일 때만 생성해 동시 요청에서도 제한을 지킨다.
- 생성은 `201 Created`와 `/api/properties/{propertyId}` Location을 반환한다.

### 목록과 진행률

- 목록은 `query`, `page`, `size`를 받는다. 페이지는 0부터 시작하고 크기는 기본 20, 최대 50이다.
- 검색어는 trim 후 이름 부분 일치에 사용한다.
- 정렬은 `last_activity_at DESC, id DESC`로 고정한다.
- 목록 SQL은 소유 회원 조건을 항상 포함한다.
- 체크 결과 전체 개수와 `GOOD`·`CAUTION` 완료 개수를 조건부 집계해 N+1 없이 진행률을 반환한다.
- 진행률은 `완료 개수 * 100 / 전체 개수`의 정수이며 항목이 없으면 0이다.
- 사진 기능이 범위 밖이므로 사진 미리보기는 이번 응답에 포함하지 않는다.

### 상세, 수정, 삭제

- 상세는 기본 정보, 메모, 단계별 체크 요약과 전체 진행률을 반환한다.
- 수정 요청은 누락 필드와 명시적 `null`을 구분한다. 누락은 기존 값을 유지하고 선택 필드의 `null`은 값을 지운다.
- 이름은 수정 시에도 `null` 또는 공백이 될 수 없다.
- 상세·수정·삭제 저장소 메소드에는 회원 ID 조건을 포함한다.
- 생성·기본 정보 수정·메모 저장·체크 결과 저장·체크리스트 적용/교체 시 `last_activity_at`을 갱신한다.
- 삭제는 DB 외래 키 연쇄 삭제를 이용하되 서비스 트랜잭션 안에서 소유권을 먼저 검증한다.

## 3. 매물 메모

- 매물당 `property_memos` 루트는 최대 하나다.
- 조회 시 루트가 없으면 빈 항목 배열, 빈 자유 메모, 저장 시각 `null`을 반환한다.
- 저장 요청은 구조화 항목 전체와 자유 메모 전체를 한 번에 전달한다.
- 구조화 항목은 최대 20개이며 label은 trim 후 1~30자, content는 최대 200자다. 자유 메모는 최대 2,000자다.
- 저장소는 루트를 insert 또는 update하고 기존 항목을 삭제한 뒤 요청 배열 순서대로 `display_order` 1부터 다시 삽입한다.
- 루트 저장, 항목 전체 교체, 매물 활동 시각 갱신은 하나의 트랜잭션이다.

## 4. 매물 체크리스트 적용과 교체

### 요청 단위

- 사용자 체크리스트 구성 수정은 이름과 전체 항목 배열을 한 번에 `PUT`한다.
- 매물 적용·교체는 특정 단계에 사용자 체크리스트 ID 하나를 `PUT`한다.
- 체크 결과 상태와 메모는 항목 하나씩 독립된 `PATCH` 요청으로 저장한다.

### 스냅샷

- 한 매물에는 단계별 체크리스트가 최대 하나 존재한다.
- 최초 적용 시 사용자 체크리스트 이름·단계와 시스템 항목 ID·질문·안내·표시 순서를 복사한다.
- 원본 사용자 체크리스트의 이후 수정·삭제·시스템 항목 비활성화는 기존 스냅샷에 영향을 주지 않는다.
- 신규 스냅샷 항목은 `UNCONFIRMED`와 빈 메모로 생성한다.

### 교체와 결과 승계

- 교체 전 기존 항목을 시스템 항목 ID 기준으로 상태·메모 맵에 담는다.
- 기존 스냅샷 항목을 모두 삭제하고 새 체크리스트 항목을 새 ID로 삽입한다.
- 시스템 항목 ID가 같은 항목만 기존 상태와 메모를 승계한다.
- 질문 문구가 같더라도 시스템 항목 ID가 다르면 신규 항목으로 취급한다.
- 새 항목은 기본 상태로 추가하고 제거된 항목 결과는 삭제한다.
- 적용/교체, 항목 삽입, 활동 시각 갱신 전체를 한 트랜잭션으로 처리한다.

## 5. 체크 결과와 진행 현황

- 상태는 `UNCONFIRMED`, `GOOD`, `CAUTION`만 허용한다.
- 상태 변경 SQL은 `status`만 변경하고 메모 변경 SQL은 `memo`만 변경한다.
- 메모는 최대 500자이며 빈 문자열은 전체 삭제 의미다.
- 변경 SQL은 회원 ID, 매물 ID, 매물 체크리스트 ID, 항목 ID를 모두 조건으로 사용한다.
- 교체 전 항목 ID나 다른 회원의 자원은 `PROPERTY_CHECKLIST_ITEM_NOT_FOUND`와 `404`를 반환한다.
- `GOOD`과 `CAUTION`은 완료, `UNCONFIRMED`는 미확인이다.
- 단계별로 전체·완료·괜찮음·주의·미확인 개수와 정수 진행률을 계산한다.
- 전체 진행률은 모든 단계 항목을 합쳐 같은 규칙으로 계산하며 항목이 없으면 0이다.

## 6. 오류와 테스트

- 요청 검증 오류는 `400`, 인증 실패는 `401`, 자원 없음과 소유권 실패는 `404`, Refresh Token 재사용과 제한 충돌은 정책에 맞는 `409`로 매핑한다.
- 필터와 전역 예외 처리기는 같은 오류 응답 구조를 사용한다.
- 오류 로그에는 토큰, OAuth 코드, 메모 원문을 포함하지 않는다.
- 저장소 통합 테스트로 잠금 조회, 소유권 조건, 부분 수정, 페이징 집계와 독립 필드 업데이트를 검증한다.
- 서비스 통합 테스트로 토큰 회전·재사용 전체 폐기, 51번째 매물 거부, 메모 롤백, 체크리스트 교체 승계와 롤백을 검증한다.
- 컨트롤러 테스트로 상태 코드, Location, 공통 응답, 필터 `401`, 누락과 명시적 `null`을 검증한다.
